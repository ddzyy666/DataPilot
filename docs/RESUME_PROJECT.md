## 30 秒项目介绍

这是一个面向业务人员的 Text-to-SQL 数据分析 Agent。它和普通 Demo 的区别是，不会直接把模型生成的
SQL 拿去执行，而是先读取 Schema 和匹配业务指标，再经过语义审核、AST 安全校验和风险评估；遇到
歧义会向用户追问，高风险 SQL 会暂停等待审批，执行失败还能自动修复。查询成功后，前端会展示中文
结论、数据画像和图表。我还建立了 50 条结果级评测集，最佳准确率达到 92%。

## 3 分钟项目介绍

项目要解决的是业务人员不会写 SQL，以及纯 LLM 生成 SQL 不稳定、不安全的问题。

第一层是上下文。我通过 SQLAlchemy 自动读取数据库结构，同时增加结构化语义层，把“销售额”“销量”
“客单价”等词映射为确定的公式、默认过滤条件和关联表，避免只靠 Prompt 猜业务口径。

第二层是 Agent 编排。我使用 LangGraph 把整个流程拆成多个业务节点。问题有歧义时通过 interrupt 暂停，
用户回答后按照 request_id 从 checkpoint 恢复；高风险 SQL 也使用相同机制等待人工批准、修改或拒绝。

第三层是可靠性。SQL 在执行前会经过 Reviewer 和 SQLGlot AST 校验，只允许查询白名单表字段，并限制
结果行数和超时。执行失败时，模型结合数据库错误和语义上下文修复 SQL，修复结果不能绕过安全检查。

第四层是结果交付。程序负责计算数值画像，模型负责生成中文洞察，前端根据字段结构自动推荐指标卡、
折线图、柱状图或表格。最后，我通过 50 条 Golden SQL 做结果级回归，最佳通过 46 条，并保留失败样例
持续分析。

## 高频面试追问

### 为什么使用 LangGraph，而不是把逻辑写在一个函数里？

项目存在澄清和人工审批两类中断场景，需要持久化状态并在后续请求中恢复。LangGraph 的 State、
Conditional Edge、Interrupt 和 Checkpoint 能显式表达业务路径，也便于独立测试每个节点。

### 如何判断生成的 SQL 正确？

分三层判断：SQLGlot 检查语法、只读性和权限；Reviewer 检查问题、Schema、语义口径与 SQL 的一致性；
离线评测执行生成 SQL，并将查询结果与标准 SQL 的结果严格比对，而不是只比较字符串。

### 业务语义层解决了什么问题？

Schema 只说明字段“长什么样”，语义层说明字段和指标“在业务上代表什么”。例如销售额必须过滤已支付
订单，并使用订单明细成交单价，而不是商品当前标价。生成、审核和修复共用同一个业务口径。

### 如何避免模型生成危险 SQL？

不依赖 Prompt 声明，而是使用 SQLGlot 解析 AST，只允许查询节点，并进行表字段白名单、行数和超时限制。
复杂 SQL 进入风险分级，高风险查询必须人工确认，人工修改后仍要重新校验。

### 为什么准确率不是 100%？

失败主要来自复杂业务条件组合、排序细节和模型理解偏差。项目保留每条失败用例及生成 SQL，通过增加语义
定义、改进 Prompt、Reviewer 和回归测试持续优化。92% 是特定模型和固定数据集上的最佳实测，不是任意
数据库的通用准确率。
